# 严谨的工作流与交付门禁 (Workflow & Quality Gates)

## 一、双轨驱动：SDD + TDD 融合模式
- **SDD (规范先行)**: 任务拆分必须先定义核心接口、边界条件和数据流向。在计划中必须回答：“这个修改的核心原理是什么？输入输出格式是什么？影响了哪些现有模块？”
- **TDD (测试先行)**: 写功能代码前，**必须先写测试用例** (定义 `.test.ts` 文件)。
- **测试标准**: 让测试用例成为自动化的“验收专家”。必须提供覆盖正常路径、异常路径（特别是网络超时、Stream 中断等边界错误）的单元/集成测试。当且仅当功能代码使测试“由红变绿”时，功能才算实现。

## 二、以 ROADMAP.md 为中心的全局连贯追踪
- **状态真相源**: 项目必须以根目录下的 `ROADMAP.md` 作为唯一的导航灯塔和状态真相源。
- **进度同步**: 每次开启新会话或执行新的 Phase 时，AI 必须首先阅读 `ROADMAP.md` 以获取当前项目的全局进度、接下来的任务规划以及验收标准。
- **持续维护**: 每个 Phase 的拆分任务、验收结论与补充说明必须首先回写到 `ROADMAP.md`。当前阶段的补充文档统一放在 `docs/` 下对应目录（如 `docs/plans/`、`docs/reviews/`），已完成的历史过程产物统一归档到 `_archive/process/`。
- **路径约束**: 不要在仓库根目录重新创建 `SPEC.md`、`TASK_TRACKER.md`、`WALKTHROUGH_PHASE*.md`、`CODE_REVIEW_PHASE*.md` 等过程文件；需要保留历史记录时，应移动或写入到上述文档目录和归档目录。

## 三、三道质量门禁
提交任何代码前，必须连续通过以下自动验证：
1. `npm run typecheck`（0 个类型错误，严禁滥用 `any` 和 `as` 强转）
2. `npm run build`（编译无误）
3. `npm test`（全量测试 100% 绿灯）

## 四、强制代码评审
每个 Phase 提交后，强制触发自动深度代码评审工作流（见 `.agents/workflows/code-review.md`），评审报告默认放在 `docs/reviews/`，历史 Phase 评审归档到 `_archive/process/reviews/`。高优先级（安全、宕机、核心逻辑）问题必须立刻修复并补提。
