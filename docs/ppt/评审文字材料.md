## 材料一：项目情况

### 一、项目背景与要解决的问题

中孚互联网大模型平台已接入完整的模型矩阵：互联网模型从轻量的 MiniMax2.5 到旗舰 GLM-5.2，另有私有部署的 Qwen3.6 系列——好比一家科室齐全的医院。但在实际使用中，模型资产的价值没有充分释放，问题在于缺少"分诊台"式的调度，集中表现为三个现象：

1. **感冒也挂专家号（资源浪费）**：Claude Code、CodeX 等 AI 编程助手是 Agent 形态，每一次对话自动产生大量背景请求（读文件、确认状态、工具回调），复杂度天差地别，却 100% 打给同一个高档模型，隐性浪费随使用规模持续放大；
2. **专家号全靠拼手速（限额错配）**：GLM-5.2有日/周限额，先到先得——抢到限额的不一定是真正需要它的任务，复杂任务反而可能被迫降级；
3. **一个科室排长队、隔壁门可罗雀（负载不均）**：请求凭个人习惯集中在 DeepSeek-v4-flash / MiniMax-M3 等个别模型上，模型矩阵的价值没有充分释放。

根因是同一个——模型矩阵不缺模型，缺的是"分诊台"式的自动调度。本项目就是补上这一层。

### 二、项目主要内容

NexusRouter 是部署在平台前的智能模型调度层，核心机制为"三级分类、四级调度"：

- **三级级联分类**：L0 规则层（中英双语高精度规则短路，约 0.05ms）→ L1 启发式层（信号驱动的档位判定，<2ms）→ L2 语义层（可选，由公司私有部署的 Qwen3.6 充当语义判官，0 API 成本）。分类判定全部本地完成，不消耗任何互联网模型 token。
- **四级调度映射**：SIMPLE → MiniMax2.5（背景请求）、MEDIUM → MiniMax2.7（常规编码）、COMPLEX → DeepSeek-v4-flash（复杂分析）、REASONING → GLM-5.1/5.2（严格推理）。旗舰限额从"先到先得"变为"按需分配"。

接入做到"三个零、两个自由"：零学习成本（客户端改 baseurl、模型填 auto 即可）、零接入改造（OpenAI / Anthropic 双协议，主流 Agent 即插即用）、零安装门槛（npm 一行命令）；模型选择自由（填具体模型名即旁路路由直连）、部署方式自由（个人本地或服务侧集中部署均可）。

项目从立项起就明确两条验收标准，并让标准决定设计取舍：**① 响应时间可控**——分类串行在转发之前，延迟 1:1 叠加到首字时间，故路由引入延迟必须无感（实测 <1ms，即使启用语义层也仅占上游首字时间的 10% 以内）；**② 复杂任务零欠档**——判错代价不对称，欠档是质量事故、过档只是多花钱，故升档必须由具体信号驱动，宁可过档不可欠档。

分类质量靠数据驱动的自我反馈闭环保障：每次路由决策全量落日志，定期分析分布与偏差。开发期间曾通过 165 条真实日志发现"无条件升档棘轮"的系统性缺陷（流量集体打到最高档、路由形同虚设），修复决策结构后建立 53 条中英文回归测试门禁，此后每次改动自动校验——每条分类规则背后都有日志证据或测试用例。

### 三、AI 应用方式

本项目本身是 AI 基础设施：语义判官层将公司私有部署的大模型用作分类器，恰到好处地盘活了私有模型资产，以 0 API 成本把公司全部模型串联成有机的调度整体。

同时，项目全程采用重度 Vibe Coding 开发（代码、测试、文档约 100% 由 AI 生成），并在过程中沉淀出开源 AI 工程工作流框架 NexusRhythm（状态机驱动、三门禁挂钩提交、多智能体分工、记忆蒸馏闭环），详见《AI 使用情况》材料。

### 四、取得效果（可复现验证）

项目已真实上线运行，完成个人试点与 7 人团队部署测试：

- **模型分布**：使用前（7 月）个人消耗 100% 扎堆在 DeepSeek-V4-Pro/Flash 与 MiniMax-M3；使用后（8 月）请求自然分布到四个档位模型，各归其位。
- **量化收益**：路由大屏按反事实基线逐笔重定价——同一批请求若全部走原高档模型需 ¥1.14，实际仅 ¥0.58，**成本节省 49.4%**（同期同批请求对比，剔除工作量差异）。
- **体验与质量**：路由引入延迟实测 <1ms，使用前后无任何体感差异；上线以来零欠档事故，分类行为由回归测试门禁锁定不劣化。
- **可审计**：路由日志、实时大屏、代码仓完整提交记录与设计评审文档全部开放，支持回溯验证。

### 五、创新与推广价值

三个原创设计：中英双语分层级联分类（亚毫秒、零 token 开销，传统 embedding 方案慢两个数量级且分类本身收费）、代价非对称的决策设计、反事实基线计价（节省金额可逐笔审计）。横向对比：商业路由（Not Diamond / OpenRouter Auto）验证了赛道价值但为云端收费黑盒且自曝 100-150ms 延迟；开源方案 RouteLLM 已停更、vLLM Semantic Router 需 K8s 整套重栈；网关类产品（LiteLLM / new-api）不做复杂度分类，与本项目互补而非竞争。

推广路径已完成两步（个人试点 ✅、7 人团队试点 ✅），下一步为公司级服务侧部署：挂在平台前，全员 auto 无感接入，实现旗舰限额按需分配。此外，new-api 是行业广泛使用的开源模型网关，本方案不止适用于我们公司——任何使用 new-api / one-api 的团队均可直接复用，具备作为产品向外推广的潜力。未来还可在路由层这一天然流量卡口上，生长出大模型审计、敏感请求识别与阻断能力（敏感代码定向私有模型、数据不出内网），与公司安全主业方向一致。
