# 档位语义定义（Tier Taxonomy）

> ROADMAP 任务 4.1。本文是**标注与回归集期望值的唯一依据** —— 判定分歧一律回到本文，而不是回到分类器实现。
> 依据：[2026-08-21 分类器设计评审](../reviews/2026-08-21-classifier-design-review.md)。
> 适用范围：live 链路 `HybridClassifier` 的四档输出。

## 为什么需要它

阈值（0.92 / 0.75）与关键词表都是拍出来的，因为「准确」从未被定义。没有 taxonomy，标注者会各自发明标准，评估集本身就不可信 —— 那时再谈准确率、再调阈值都是空转。

本文先定义**人应当怎么判**，实现（三层级联、关键词、置信度）是为了逼近这个判定，不是它的来源。

## 决策轴：为什么保留四档

评审曾考虑并档为 cheap / strong / reasoning 三档。结论是**保留四档**，因为真实代价结构不支持并档：

live `config.yaml` 的映射是

| 档位      | 模型                       |
| :-------- | :------------------------- |
| SIMPLE    | `claude-opus-4-8`          |
| MEDIUM    | `claude-opus-4-8-thinking` |
| COMPLEX   | `claude-opus-5`            |
| REASONING | `claude-opus-5-thinking`   |

四档实际上是两个**正交轴**的乘积：

- **能力轴**（capability）：`opus-4-8` → `opus-5`
- **思考轴**（thinking）：关 → 开

因此：

```
            thinking off      thinking on
opus-4-8    SIMPLE            MEDIUM
opus-5      COMPLEX           REASONING
```

并成三档会把这个乘积压平，丢掉「要不要 thinking」这个独立决策 —— 而它恰恰是本部署下最主要的成本项（见下）。四档不是「难度的四个刻度」，而是**两个二元问题**：需要更强的模型吗？需要它先想再答吗？

> 该结论绑定当前 config。若某部署把四档映射到能力差异悬殊的模型（如 `gpt-4o-mini` → `o3`），代价矩阵形状改变，并档结论需重估。

## 代价矩阵

评审报告纠正了讨论清单的原始假设。原假设是「该强给弱 = 质量可见崩」，但在本部署下并不成立：

| 错误方向           | 代价                             | 严重度             |
| :----------------- | :------------------------------- | :----------------- |
| 欠档（弱给强活）   | 掉一级 opus 或少一次 thinking    | 中 —— 质量略降     |
| 超档（强给弱活）   | 多付 thinking token / 更贵的模型 | 中 —— 静默多花钱   |
| 无条件超档（棘轮） | 每条请求都顶格，路由器失去意义   | 高 —— 产品价值归零 |

**关键推论**：四档全是 opus，欠档的质量代价远小于通常假设，因此「拿不准就升档」不再是免费保险。它必须有封顶（D-002 的直接根因）。

判定原则：**拿不准时倾向升一档，但升档必须由具体信号驱动，不得由「没有信号」驱动。** 缺证据是 SIMPLE 的理由，不是 REASONING 的理由。

## 四档判定规则

判定对象是**当前轮用户意图**（`extractClassificationText` 的输出：最近一条含真实文本的 user 消息，已剥离 host 注入块），不是整段会话。

### SIMPLE — 不需要更强模型，也不需要先想

一次直答即可完成，无需读取项目状态，无需多步。

- 问候、感谢、确认（「好的」「收到」）
- 事实查询（「satisfies 是哪个版本引入的」）
- 翻译、改写、格式化
- 单点查询类问题（「这个配置项默认值是多少」）

### MEDIUM — 不需要更强模型，但需要先想或需要读取状态

单一目标、路径清晰，但要动到项目里的具体位置，或需要组织一段有结构的输出。

- 局部修改（改名、调参数、加一个字段、修一处明确的笔误）
- 解释一段给定的代码
- 总结、提取、按要求生成一段文档
- 单文件范围内的问题定位

### COMPLEX — 需要更强模型：多步、跨文件、或需要判断权衡

目标明确但路径不明确，需要探索、跨多个位置协调，或需要做设计取舍。

- 新增功能（涉及多处改动）
- 跨文件重构
- 根因不明的 bug 定位
- 架构层面的分析与方案设计
- 代码评审、安全审计

### REASONING — 需要更强模型且需要严格推理链

正确性依赖可验证的推导过程，答案对错分明且不能靠经验直觉蒙对。

- 数学证明、复杂度推导
- 形式化逻辑、不变式论证
- 需要精确演算的算法正确性分析

### 判定边界（歧义时的裁决顺序）

1. **看动作，不看词汇。** 「分析」出现在「深入分析架构」是 COMPLEX，出现在「分析一下这个变量名合适吗」是 MEDIUM。触发词本身从不决定档位。
2. **看范围，不看长度。** 一句话的「重构整个调度器」是 COMPLEX；三百字详述的改名仍是 MEDIUM。
3. **filler 词不携带难度。** 「继续」「那个」「刚才」只说明这是续轮，不说明难度。剥掉这些词后按剩余内容判。若剥掉后无实质内容（纯「继续」），判 MEDIUM —— 续轮的实际工作至少是延续，但不足以推定升档。
4. **REASONING 只给推导，不给「难」。** 「这个架构很难设计」是 COMPLEX，不是 REASONING。REASONING 的判据是「有无严格推导链」，不是难度上限。
5. **区分工具「能力」与动手「意图」。** 有工具表、能否 tool-calling、上下文窗口大小属于能力筛选（`filterByToolCalling` / `maxTokensForceComplex` 的职责），与难度无关。但「这一轮要动手改动项目」是意图信号：它把 SIMPLE 提到 MEDIUM 的下限（读项目状态才能答），**不逐级累加** —— 已是 COMPLEX 的活不因为「要动手」变成 REASONING。
6. **会话长度不携带难度。** 判定只看当前轮意图。真实流量中 161/165 条都是长会话，恒定的信号不含信息（与 D-001 的 `hasTools` 同理）。
7. **拿不准取低档 + 记 `note`。** 标注阶段的犹豫应留下痕迹供复核，不应通过升档掩盖。

## 标注格式

沿用讨论清单已定的格式：路由日志原始字段 + 两个人工字段，`src/eval.ts` 已能直接消费。

```jsonc
{
  // ... routing-YYYY-MM-DD.jsonl 的原始字段，原样保留
  "expectedTier": "MEDIUM", // 必填，四档之一，依本文判定
  "note": "改名类局部修改；被 requiresTools 推到 COMPLEX", // 选填，判定理由或分歧点
}
```

规则：

- `expectedTier` 缺失的行被 `parseLabeledJsonl` 跳过（视为未标注），非法值计入 `skippedInvalid`。
- 判定依据只能是 `promptPreview` 所反映的用户意图 —— **不要**参考同一行的 `finalTier` / `layer` / `confidence`，那会把分类器的错误抄进标准答案。
- 边界样本必须写 `note`，进入 `highConfidenceMisses` 时才有复核依据。

## 采样策略

- 按 `layer` × `finalTier` 分层抽样，避免被高频层淹没。
- `layer: "fallback"` 全量纳入 —— 它是当前最大的错误来源（评审发现 1：Layer 1 阈值不可达，绝大多数流量落此层）。
- 目标 200~300 条出基线。
- **前提**：只能使用 2026-08-20 修复之后产生的日志。现有 165 条全部早于该批修复（缺 `promptCharsSanitized` 字段可识别），不可用于标注（ROADMAP 4.0）。

## 验收（本文如何算「定义成功」）

两名标注者独立标注同一批 30 条边界样本，一致率 ≥ 85%。低于此值说明规则仍有歧义，应先补判定边界条款，而不是开始大规模标注。
